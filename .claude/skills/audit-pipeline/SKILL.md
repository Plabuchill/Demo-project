## เมื่อ skill นี้ถูกเรียก

Skill นี้ตรวจสอบความสอดคล้องของเอกสารทั้งสายงานตามลำดับ: spec (`01-spec/`) → `backlog.md`/
`feature-list.md` → user journey (`01-prototypes/*.md`) → จากนั้นแยกเป็น **3 สาขาขนานกัน** ที่ต่าง
พึ่ง `feature-list.md`/journey เหมือนกันแต่ไม่ขึ้นต่อกันเอง:
- **(ก) เอกสารทดสอบ** ใน `docs/03-testing/01-test-plan/`
- **(ข) Prototype** ล่าสุดใน `docs/02-design/01-prototypes/`
- **(ค) เอกสารเชิงเทคนิค** ใน `docs/02-design/02-technical/` (มีลำดับชั้นย่อยต่อเนื่องกัน 4 ชั้น
  ดู `sync-technical-spec`)

รันตรวจ (และแก้ไขถ้าจำเป็น) ไล่จากชั้นต้นทางไปชั้นปลายทางตามลำดับ **ไม่ใช่รันขนานข้ามชั้น** สาขา
prototype และขั้นตอน `nfr-review.md` ในสาขา (ค) เป็นจุดเดียวที่**ตรวจสอบและรายงานเท่านั้น
ไม่ auto-fix**

## ขั้นตอน

1. **หาวันที่ปัจจุบัน**: รูปแบบ `YYYYMMDD` เพื่อส่งต่อให้ skill/agent ทุกตัวใช้กับไฟล์ log

2. **ชั้นที่ 1 — spec ↔ backlog ↔ feature-list**: เรียกผ่าน **Skill tool** ด้วย
   `skill: audit-feature-list` แล้วรอผลลัพธ์ก่อนไปขั้นตอนถัดไปเสมอ

3. **ตรวจสอบผลลัพธ์ชั้นที่ 1**: สุ่มอ่าน `docs/01-requirements/feature-list.md` จริงอย่างน้อย 1-2
   จุดก่อนไปต่อ ถ้าพบปัญหาเชิงโครงสร้างที่ทำให้ตรวจต่อไม่ได้ ให้หยุด pipeline ทันทีและรายงานผู้ใช้

4. **สาขา (ก) — เอกสารทดสอบ (auto-fix)**: เรียกผ่าน **Skill tool** ด้วย `skill: sync-test-plan`
   **ต้องรอชั้นที่ 1 เสร็จสมบูรณ์ก่อนเสมอ**

5. **ตรวจสอบผลลัพธ์สาขา (ก)**: สุ่มอ่าน `acceptance-criteria.md`, `test-plan.md`, และไฟล์ใน
   `test-cases/` จริงอย่างน้อย 1-2 จุด ถ้า `sync-test-plan` รายงานว่า auto-chain ไป
   `requirement-writer` ระหว่างทาง ให้บันทึกไว้สำหรับสรุปในข้อ 10 ด้วย

6. **สาขา (ข) — prototype (report-only)**: เรียก agent `prototype-auditor` ผ่าน Agent tool
   (`run_in_background: false`) **ต้องรอชั้นที่ 1 เสร็จสมบูรณ์ก่อนเสมอ** (ไม่ต้องรอสาขา (ก) เพราะ
   สามสาขานี้ไม่ขึ้นต่อกัน)

7. **ตรวจสอบผลลัพธ์สาขา (ข)**: ถ้าผลลัพธ์แสดงว่า `prototype-auditor` แก้ไข/สร้างไฟล์ใดๆ ในโฟลเดอร์
   เวอร์ชัน prototype ให้ถือว่าผิดกฎ หยุดและแจ้งผู้ใช้ทันที

8. **สาขา (ค) — เอกสารเชิงเทคนิค (auto-fix ยกเว้น NFR review)**: เรียกผ่าน **Skill tool** ด้วย
   `skill: sync-technical-spec` **ต้องรอชั้นที่ 1 เสร็จสมบูรณ์ก่อนเสมอ** (ไม่ต้องรอสาขา (ก)/(ข))

9. **ตรวจสอบผลลัพธ์สาขา (ค)**: สุ่มอ่าน `architecture.md`, `api-spec.md`/`db-spec.md`, ไฟล์ใน
   `detailed-design/`, และ `nfr-review.md` จริงอย่างน้อย 1-2 จุด ตรวจว่าไม่มีชื่อ technology/
   framework/database engine ใดๆ หลุดเข้าไป ถ้า `sync-technical-spec` รายงานว่า auto-chain ไป
   `requirement-writer` ระหว่างทาง ให้บันทึกไว้เช่นเดียวกับข้อ 5

10. **สรุปผลรวมทั้ง pipeline เป็นรายงานเดียว** แยกตามชั้น: spec/backlog/feature-list, เอกสารทดสอบ,
    prototype, เอกสารเชิงเทคนิค (รวมผล NFR review) และจุดที่ skill/agent ตัวใดถามผู้ใช้ระหว่างทาง

11. **ถ้าพบว่า prototype ล้าสมัยหรือยังไม่เคยสร้าง**: ใช้ `AskUserQuestion` ถามผู้ใช้ต่อ เสนออย่าง
    น้อย 3 ตัวเลือก: (1) รัน `build-prototype` ต่อทันทีในเทิร์นเดียวกัน **(แนะนำ)**, (2) ไว้
    ตัดสินใจรันเองทีหลัง, (3) ขอดูรายละเอียดฟีเจอร์ที่ขาดหายทั้งหมดก่อนตัดสินใจ

## ข้อควรระวัง

- **ต้องรันตามลำดับชั้นเสมอ (sequential) ห้ามรันขนานข้ามชั้น** — สาขา (ก)/(ข)/(ค) เท่านั้นที่ไม่
  ขึ้นต่อกันเอง (รันก่อนหลังกันได้ แต่ทั้งสามต้องรอชั้นที่ 1 เสร็จก่อนเริ่มเสมอ)
- ห้ามข้ามชั้นใดชั้นหนึ่งไปเอง แม้ผู้ใช้จะถามถึงแค่ปัญหาชั้นปลาย
- ห้ามข้ามการเรียก skill/agent แล้วแก้ไฟล์เองตรงๆ ในเทรดหลักไม่ว่าชั้นใด
- Agent `prototype-auditor`/`nfr-reviewer` ต้อง report-only เท่านั้น ถ้าผลลัพธ์พูดถึงการแก้ไฟล์
  เอกสารต้นทางของตัวเอง ให้ถือว่าผิดปกติ หยุดและแจ้งผู้ใช้ทันที
- `sync-test-plan`/`sync-technical-spec` มี loop guard ของตัวเองอยู่แล้ว ไม่ต้องทำ guard ซ้ำ
- **เอกสารในสาขา (ค) ต้องไม่ระบุชื่อ technology/framework/database engine ใดๆ** จนกว่า
  `technology-stack.md` จะถูกตัดสินใจแล้วจริง
- ถ้า skill/agent ตัวใดตัวหนึ่งรายงานปัญหาเชิงโครงสร้าง ให้หยุด pipeline ทันที ไม่ไปชั้นถัดไป แล้ว
  รายงานปัญหานั้นให้ผู้ใช้ก่อนเสมอ
- **`sync-phase-plan` ไม่ได้เป็นส่วนหนึ่งของ pipeline นี้โดยเจตนา** — เป็นงานวางแผนที่ต้องยืนยันกับ
  ผู้ใช้แบบโต้ตอบ ไม่ใช่งาน audit ความสอดคล้องของเอกสารที่มีอยู่แล้ว ห้ามเรียกจาก pipeline นี้เอง
