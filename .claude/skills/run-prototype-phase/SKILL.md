## เมื่อ skill นี้ถูกเรียก

1. **หาวันที่ปัจจุบัน**: รูปแบบ `YYYYMMDD` เพื่อส่งต่อให้ agent/skill ใช้กับไฟล์ log

2. **sub-step 1 — ตรวจสอบ (report-only)**: เรียก agent `prototype-auditor` ผ่าน Agent tool
   (`run_in_background: false`) พร้อมบริบท session สนทนาจริง เพื่อตรวจว่า prototype เวอร์ชัน
   ล่าสุด (ถ้ามี) ยังครอบคลุมฟีเจอร์ Must ทั้งหมดใน `feature-list.md`/เอกสาร journey ปัจจุบันหรือไม่

3. **ตรวจสอบผลลัพธ์ sub-step 1**: ถ้าผลลัพธ์แสดงว่า `prototype-auditor` แก้ไข/สร้างไฟล์ใดๆ ใน
   โฟลเดอร์เวอร์ชัน prototype ให้ถือว่าผิดกฎ หยุดและแจ้งผู้ใช้ทันที

4. **ถ้า up to date อยู่แล้ว หรือยังไม่เคยมีฟีเจอร์ Must ใดต้องมี prototype**: สรุปผลจบได้เลยที่
   ข้อ 7 ไม่ต้องทำ sub-step 2

5. **ถ้าล้าสมัยหรือยังไม่เคยสร้าง**: ใช้ `AskUserQuestion` ถามผู้ใช้ต่อทันที เสนออย่างน้อย 3
   ตัวเลือก: (1) รัน `build-prototype` ต่อทันทีในเทิร์นเดียวกัน **(แนะนำ)**, (2) ไว้ตัดสินใจรันเอง
   ทีหลัง, (3) ขอดูรายละเอียดฟีเจอร์ที่ขาดหายทั้งหมดก่อนตัดสินใจ

6. **sub-step 2 — สร้าง/แก้ไข (เฉพาะถ้าผู้ใช้เลือกตัวเลือก (1))**: เรียกผ่าน **Skill tool** ด้วย
   `skill: build-prototype` ปล่อยให้ skill นี้จัดการขั้นตอนยืนยัน scope กับผู้ใช้เอง

7. **สรุปผลรวมเป็นรายงานเดียว** แยกตาม sub-step: ตรวจสอบ (up to date หรือไม่, ฟีเจอร์ที่ขาดหาย/
   ล้าสมัย), สร้าง/แก้ไข (ถ้าทำ), จุดที่ถาม/รอผู้ใช้ตัดสินใจระหว่างทาง

## ข้อควรระวัง

- **ต้องทำ sub-step 1 ก่อนเสมอ ห้ามข้ามไปเรียก `build-prototype` ตรงๆ** แม้ผู้ใช้จะขอ "อัปเดต
  prototype" มาตรงๆ ก็ตาม
- ห้ามข้ามการเรียก agent/skill แล้วแก้ไฟล์ HTML เองตรงๆ ในเทรดหลัก
- Skill นี้ scope แค่ "ช่วง prototype" เท่านั้น — ถ้า `prototype-auditor`/`build-prototype` รายงาน
  ว่าเอกสารต้นทาง (`feature-list.md`/journey) ไม่พร้อม ให้แจ้งผู้ใช้ว่าควรรัน `audit-feature-list`/
  `create-user-journey` ก่อน แทนการฝืนทำต่อ
- ถ้า agent/skill ตัวใดตัวหนึ่งรายงานปัญหาเชิงโครงสร้าง ให้หยุดและรายงานผู้ใช้ก่อนเสมอ
